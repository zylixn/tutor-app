# 家教小程序 — 项目优化提案

> **生成日期**: 2026-06-28
> **审查范围**: Go 后端 + 微信小程序前端
> **审查方法**: 基于代码走查 + 架构分析

---

## 一、当前项目状态概览

| 维度 | 现状 |
|------|------|
| 后端 | Go + Gin + SQLite，6 个 API 端点，JWT 鉴权，CORS 中间件 |
| 前端 | 微信小程序原生开发，4 个页面，3 个组件，1 个 Behavior |
| 数据库 | SQLite 单文件，3 张表（tutors / reviews / users），含测试数据 |
| 认证 | 自实现 JWT（HMAC-SHA256），登录仅 mock（`dev_openid_` + code） |
| 部署 | 无 Docker/CI/CD，无 HTTPS，无域名配置 |

## 二、优化项清单

### P0 — 安全/可靠性（必须修复）

#### P0-1 登录接口为 Mock 实现，无真实微信鉴权

**问题**: `handlers/reviews.go:29` 硬编码 `openID := "dev_openid_" + req.Code`，任何前端传入任意 code 即可登录，无微信 code2session 调用。

**修复方案**:
1. 调用微信 `sns/jscode2session` 接口，用 AppID + AppSecret + code 换取真实 openid
2. 配置中新增 `WECHAT_APP_ID` 和 `WECHAT_APP_SECRET` 环境变量
3. 开发环境保留 mock 模式（通过 `GO_ENV=development` 开关）

```go
// 伪代码
func getWeChatOpenID(code string) (string, error) {
    if os.Getenv("GO_ENV") == "development" {
        return "dev_openid_" + code, nil
    }
    resp, err := http.Get(fmt.Sprintf(
        "https://api.weixin.qq.com/sns/jscode2session?appid=%s&secret=%s&js_code=%s&grant_type=authorization_code",
        cfg.WechatAppID, cfg.WechatAppSecret, code))
    // 解析返回的 openid
}
```

**工作量**: 2h

---

#### P0-2 JWT Secret 硬编码默认值

**问题**: `config/config.go:34` 当 `JWT_SECRET` 未设置时使用 `"dev-secret-change-in-production"`，生产环境若忘记配置则任何人可伪造 token。

**修复方案**:
1. 生产环境启动时若 `JWT_SECRET` 为空或等于默认值，**拒绝启动**
2. 新增 `GO_ENV` 环境变量区分环境

```go
if config.JWTSecret == "" || config.JWTSecret == "dev-secret-change-in-production" {
    if os.Getenv("GO_ENV") == "production" {
        return nil, fmt.Errorf("生产环境必须设置 JWT_SECRET")
    }
    config.JWTSecret = "dev-secret-change-in-production"
    log.Println("⚠️  使用开发默认 JWT_SECRET，生产环境必须配置！")
}
```

**工作量**: 0.5h

---

#### P0-3 评论接口无重复提交防护

**问题**: 同一用户可对同一家教无限次提交评论。

**修复方案**: 在 `SubmitReview` 中增加唯一性校验：

```go
var existing int
err := database.DB.QueryRow(
    "SELECT COUNT(*) FROM reviews WHERE tutor_id = ? AND user_id = ? AND status = 'active'",
    req.TutorID, userID).Scan(&existing)
if existing > 0 {
    c.JSON(http.StatusConflict, gin.H{"error": "您已评论过该家教"})
    return
}
```

或在数据库层加 UNIQUE 约束：`UNIQUE(tutor_id, user_id)`。

**工作量**: 1h

---

#### P0-4 微信号脱敏逻辑可被绕过

**问题**: `models/tutor.go:72-79` 的 `MaskWechatID` 是在 Go 层面脱敏，但家教列表 API 返回的是 `MaskWechatIDs(tutors)` 后的结果。而家教详情 API 的评论中 `user_id` 完整暴露，存在用户枚举风险。

**修复方案**:
1. 评论返回中 `userId` 脱敏或移除
2. 考虑是否需要"联系家教"的专用接口，而非在详情中返回微信号（即便是脱敏的）

**工作量**: 1h

### P1 — 架构/可维护性（强烈建议）

#### P1-1 数据库层缺少 Repository 抽象

**问题**: `handlers/tutors.go` 和 `handlers/reviews.go` 直接写 SQL 查询，业务逻辑与数据访问耦合。新增功能（如收藏、预约）时，SQL 会散落各处。

**修复方案**: 引入 Repository 层：

```
backend/
  repository/
    tutor_repo.go    # TutorRepository interface + 实现
    review_repo.go   # ReviewRepository interface + 实现
  handlers/          # 只处理 HTTP 请求/响应，调用 repo
```

好处：
- 便于单元测试（可 mock repo）
- 便于未来切换数据库（PostgreSQL / MySQL）
- SQL 集中管理

**工作量**: 4h

---

#### P1-2 缺少请求日志和结构化日志

**问题**: 当前仅有 `log.Printf`，无请求 ID、无响应时间、无结构化输出，生产排查困难。

**修复方案**:
1. 引入 `gin.Logger()` 替代或使用 `logrus` / `slog`
2. 每个请求分配 requestID
3. 关键操作（登录、评论、创建家教）记录结构化日志

```go
router.Use(func(c *gin.Context) {
    start := time.Now()
    requestID := uuid.New().String()[:8]
    c.Set("requestID", requestID)
    c.Header("X-Request-ID", requestID)
    c.Next()
    log.Printf("[%s] %s %s %d %v",
        requestID, c.Request.Method, c.Request.URL.Path,
        c.Writer.Status(), time.Since(start))
})
```

**工作量**: 2h

---

#### P1-3 前端缺少错误边界和全局错误处理

**问题**: `utils/api.js` 的 `fail` 回调仅 `reject(err)`，页面 catch 后只 `wx.showToast`，无重试机制、无统一错误页面、网络断开时体验差。

**修复方案**:
1. `api.js` 增加重试逻辑（指数退避，最多 3 次）
2. 新增 `components/error-page` 组件（空状态 + 重试按钮）
3. App 层监听 `wx.onNetworkStatusChange`，全局提示网络状态

**工作量**: 3h

---

#### P1-4 缺少 API 接口文档

**问题**: 无 Swagger/OpenAPI 文档，新成员上手靠读代码。

**修复方案**:
1. 引入 `swaggo/swag`，在 handler 上加注释自动生成文档
2. 开发环境暴露 `/swagger/*` 路由

```go
// @Summary 获取家教列表
// @Tags tutors
// @Param subject query string false "科目"
// @Success 200 {object} models.TutorListResponse
// @Router /api/v1/tutors [get]
func GetTutors(c *gin.Context) { ... }
```

**工作量**: 2h

---

#### P1-5 SQLite 不支持并发写入

**问题**: SQLite 单写锁，多用户同时提交评论时可能遇到 `database is locked` 错误。

**修复方案**:
1. 短期：增加 `PRAGMA journal_mode=WAL;` 和合理的 busy_timeout
2. 中期：评估迁移到 PostgreSQL（当并发 > 10 QPS 时）

```go
// database/db.go
db.SetMaxOpenConns(1) // SQLite 写入串行化
db.Exec("PRAGMA journal_mode=WAL")
db.Exec("PRAGMA busy_timeout=5000")
```

**工作量**: 1h（短期）/ 8h（迁移 PG）

### P2 — 功能完善（建议实现）

#### P2-1 家教申请/入驻流程

**问题**: 当前只能通过 admin API 创建家教，无自助入驻入口。

**方案**:
1. 新增 `pages/tutor-apply` 页面
2. 后端新增 `POST /api/v1/tutors/apply`（需登录，status 默认 `pending`）
3. Admin 后台审核（设为 `verified=true` + `status=active`）

**工作量**: 8h

---

#### P2-2 收藏/关注功能

**问题**: 家长无法收藏感兴趣的家教，只能浏览。

**方案**:
1. 新增 `favorites` 表 `(user_id, tutor_id, created_at)`
2. 新增 `POST/DELETE /api/v1/favorites` 端点
3. 前端家教详情页加收藏按钮，"我的"页加收藏列表

**工作量**: 6h

---

#### P2-3 搜索关键词高亮 + 模糊搜索增强

**问题**: 当前搜索只支持科目/年级/地点精确匹配，无关键词全文搜索（如搜"北大"搜不到 `school=北京大学` 的家教）。

**方案**:
1. 后端 `GetTutors` 增加 `keyword` 参数，搜索 name / school / bio / major 字段
2. 前端搜索结果中高亮匹配词

**工作量**: 4h

---

#### P2-4 管理后台

**问题**: 当前管理家教只能通过 API（curl/Postman），无可视化界面。

**方案**:
1. 选项 A：小程序内嵌 admin 页面（仅 admin 角色可见）
2. 选项 B：独立 Web 管理后台（React/Vue）
3. 建议先选 A 快速验证，后续再建独立后台

**工作量**: 12h（选项 A）/ 40h（选项 B）

#### P2-5 图片上传

**问题**: 家教头像、资质证明目前只有路径字段，无实际上传能力。

**方案**:
1. 后端新增 `POST /api/v1/upload`，存储到本地/对象存储

**工作量**: 6h

**工作量**: 2h

#### P3-2 家教列表虚拟滚动

**问题**: 当家教数据量 > 100 条时，`setData` 全量更新导致卡顿。

**方案**: 引入 `recycle-view` 组件或分页懒加载优化。

#### P3-3 API 响应缓存

**问题**: 每次打开首页都请求后端，无本地缓存。

**方案**:
1. 前端 `wx.setStorage` 缓存家教列表（5 分钟 TTL）

**工作量**: 3h

---

#### P3-4 后端健康检查缺少数据库连接检测

**问题**: `/health` 仅返回 `{"status": "ok"}`，未检查数据库连接。

**方案**:
```go
router.GET("/health", func(c *gin.Context) {
    var ok string
    err := database.DB.QueryRow("SELECT 'ok'").Scan(&ok)
    if err != nil {
        c.JSON(503, gin.H{"status": "unhealthy", "db": err.Error()})
        return
    }
    c.JSON(200, gin.H{"status": "ok", "db": "connected"})
})
```

**工作量**: 0.5h

---

#### P3-5 前端缺少下拉刷新

**问题**: `pages/index/index.js` 有 `loadTutors` 但未注册 `onPullDownRefresh`。

**方案**: 在 index 和 tutor-list 页面添加下拉刷新支持。

**工作量**: 1h

## 四、技术债务记录

| 债务 | 影响 | 偿还时机 |
|------|------|----------|
| SQLite 单文件写入锁 | 并发 > 10 QPS 时瓶颈 | 用户量达 500+ 时迁移 PG |
| 无数据库迁移工具 | Schema 变更无版本管理 | P2-1 实现时引入 golang-migrate |
| 前端无状态管理 | 页面间数据靠 URL 传参 | 页面 > 8 个时引入全局 store |
| 无自动化测试 | 回归靠手动 | P1-1 完成后补充单元测试 |
| `search-bar` 组件空目录 | 未实现的组件 | P2-3 搜索增强时一并实现 |
| `tutor-api` 二进制 17MB 提交到 git | 仓库膨胀 | 加入 .gitignore，CI 构建 |

---

## 五、总结

当前 MVP 已完成核心功能闭环（搜索→详情→联系→评论），可支撑初步验证。优先修复 P0 安全问题后即可上线内测。P1 架构优化为后续功能扩展打基础，建议在第 2 周完成。P2 功能按业务优先级逐步实现。

**最小可上线集**：P0 全部 + P3-4 健康检查 ≈ 5.5h 工作量。
