# 看板格式强约束

> 本文件由 daily-report skill 加载，适用于看板源文件的新建/更新场景。
> 看板源文件是单一可信源（SSOT），AI 不得随意修改看板结构与字段约定。
> 配套文档：`kanban-template.md`（通用模板）、`kanban-guide.md`（查询展示指南），与本文件同目录。

## 1. 适用范围

适用于 `reports/<YYYY>/knowledge/*_kanban*.md` 看板源文件的：
- 新建（战役启动）
- 任务行更新（状态推进、Owner 变更、Deadline 调整、备注补充）
- 风险登记、关键路径维护

**兼容策略**：
- **新建/初始化看板**：必须使用本文件定义的当前格式，含「迭代开发版本号」元数据和「对应研发系统需求号」列；缺失即 P0。
- **更新历史旧看板**：允许 legacy 格式继续更新，不因缺少「迭代开发版本号」或「对应研发系统需求号」列而拒绝；`kanban-update.js` 会输出 WARN 并建议迁移。除这两个兼容字段外，状态枚举、Owner 所有权校验、任务编号、汇总重算仍然强制执行。
- **旧看板迁移**：一旦对结构做非状态类维护（新增任务、重排 Sprint、补充元数据），应同步迁移到当前模板。

**不适用于**看板**展示视图**（团队/个人看板查询渲染由 `daily-report/docs/kanban-guide.md` 规范）。

## 2. 必须保留的 8 个结构块（顺序固定，缺一即 P0）

| # | 结构块 | Markdown 层级 | 强制内容 |
|---|--------|--------------|---------|
| 1 | 标题 + 版本号 | `H1` | `# {战役} 看板 v{X.Y} {STATUS}` |
| 2 | 元数据引用块 | `>` quote | 迭代开发版本号 / 基线 / 更新频率 / 本次更新 / 状态定义 / 主线命名 |
| 3 | 总览统计（4 张表） | `## 总览` | Sprint 总览 / 类别分布 / 按人员 / 按工作域 |
| 4 | Sprint N 任务区 | `## Sprint N · 名称` | 至少 1 个 Sprint，含退出标准 + 主线分组任务表 |
| 5 | 关键路径 | `## 关键路径` | P0 路径链路图（code block） |
| 6 | 风险登记簿 | `## 风险登记簿` | 表格 + 至少 1 条风险 |
| 7 | 分隔符 | `---` | 各 Sprint 之间、结构块之间 |
| 8 | 最后更新脚注 | `*italic*` | `*最后更新：YYYY-MM-DD HH:MM by ...*` |

**禁止**：调换结构块顺序、删除任一结构块、改变层级。

### 2.1 元数据引用块字段规范（6 字段，缺一即 P0）

| 字段 | 格式 | 示例 |
|------|------|------|
| **迭代开发版本号** | `{产品}_{版本}_{YYYYMMDD}` | `MOGP_V2.5.0_20260530` |
| **基线** | `{spec 文件} v{版本}（🔒 {锁定日期}）` | `630-unified-spec-LOCKED.md v1.0（🔒 2026-06-11）` |
| **更新频率** | `每日 {HH:MM} by {PM}` | `每日 23:59 by qiuyong` |
| **本次更新** | `v{X.Y}（{YYYY-MM-DD HH:MM}）— {摘要 ≤ 80 字}` | `v3.3（2026-06-13 23:22）— S0-14 完成 + D-18 进行中` |
| **状态定义** | 固定 5 emoji 枚举 | `⬜ 未开始 \| 🔵 进行中 \| 🟡 有风险 \| 🔴 阻塞 \| ✅ 完成` |
| **主线命名** | `{名称}({前缀})` 列举 | `安全(A) / 部署(B) / 稳定(C)` |

**「迭代开发版本号」格式约束**：
- 三段式：`{产品代号}_{语义化版本}_{发布日期 YYYYMMDD}`
- 产品代号大写（如 `MOGP`、`BPCE`），版本遵循 `vX.Y.Z`（主.次.修订），日期为计划发布日
- 一个战役内版本号唯一，战役内迭代升级时（如 v2.5.0 → v2.5.1）须更新此字段并同步"本次更新"

**禁止**：
- ❌ 字段缺失（必须 6 个字段全填）
- ❌ 版本号格式不符（如 `v2.5`、`V2.5.0`、`2.5.0`）
- ❌ 用 git commit hash 或时间戳冒充版本号

## 3. 任务表列规范（列固定，禁止新增/删除/调换/改名）

**标准 7 列**（顺序固定）：

```markdown
| # | 任务 | 对应研发系统需求号 | Owner | Deadline | 状态 | 备注 |
```

**Sprint 0 例外**：可在 `状态` 之后插入 `主线` 列，用于跨主线追溯，形成 8 列：

```markdown
| # | 任务 | 对应研发系统需求号 | Owner | Deadline | 状态 | 主线 | 备注 |
```

**禁止**：
- ❌ 新增列（如"工时"、"进度%"、"评估人"）
- ❌ 删除任一列（含「对应研发系统需求号」）
- ❌ 调换列顺序
- ❌ 改列名（"任务" 不能改成 "Task"/"描述"/"内容"；"对应研发系统需求号" 不能改成 "需求号"/"Jira"/"Req"）

### 3.1 「对应研发系统需求号」列规范

| 场景 | 填写 | 示例 |
|------|------|------|
| 单需求 | `{REQ-ID}` | `REQ-2026-001` |
| 多需求 | `{REQ-ID1} + {REQ-ID2}` | `REQ-2026-001 + REQ-2026-002` |
| 无对应 | `—`（半角破折号，**禁止留空**） | `—` |

**格式约束**：
- 必须是研发系统（如禅道/JIRA/TAPD）的可追溯 ID，禁止填写任务描述或自创编号
- 一个战役内的需求号风格统一（同一研发系统同一种格式）
- 多需求用 ` + ` 分隔（与 Owner 列一致）
- 任务流转过程中需求号变更时，更新此列（旧号删除，不保留历史）

**禁止**：
- ❌ 列留空
- ❌ 填写文字描述（如"见设计文档"、"待补"）
- ❌ 用看板自身任务编号（如 `D-07`）冒充研发系统需求号

## 4. 状态枚举（封闭集合，禁止扩展）

| Emoji | 状态 | 含义 |
|-------|------|------|
| ⬜ | 未开始 | 默认值，新建任务初始态 |
| 🔵 | 进行中 | 已启动 |
| 🟡 | 有风险 | 进度落后或阻塞预警 |
| 🔴 | 阻塞 | 阻塞中，需 PM 介入 |
| ✅ | 完成 | 验收通过 |

**禁止**：
- ❌ 自创 emoji（🟢🟠⛔🚫❌⚠️ 等）
- ❌ 混用文字状态（"已完成"/"进行中"/"done"）
- ❌ 状态留空

## 5. 任务编号规范

格式：`{前缀}-{数字}` 或 `{前缀}{数字}`（同一战役内统一一种风格）。

**已注册前缀**（来自 `CLAUDE.md §0.5`，新增前缀须先更新 CLAUDE.md）：

| 前缀 | 主线 |
|------|------|
| `S0-` | Sprint 0 准备 |
| `A-` | 安全主线 |
| `B-` | 部署主线 |
| `C-` | 稳定主线 |
| `D-` | 价值主线 |
| `E-` | 交付使能线 |
| `F-` | 场景验证线 |
| `H-` | 驾驭工程 |
| `I-` | 交互 UI |
| `UX-` | 产品体验 |
| `V-` | E2E 验收 |
| `BP-` | 场景准备 |
| `REL-` | 发布 |
| `PG-` | 产品门禁 |

**禁止**：
- ❌ 自创前缀（如 `X-`、`T-`、`Z-`）
- ❌ 无前缀的任务编号（如 `01`、`Task1`）
- ❌ 同一战役内编号复用（编号唯一）

## 6. 备注列规范

### 6.1 优先级标记（必须前置）

| 标记 | 加粗 | 含义 |
|------|:----:|------|
| `**P0**` | 是 | 商用阻断，**必须**附验收口径 |
| `**P1-Tech**` | 是 | 技术探索性 P1（不阻断发布） |
| `P1` | 否 | 一般 P1 |
| `P2` | 否 | 低优先级 |

**未标优先级的任务默认视为 P1**，但仍建议显式标注。

### 6.2 辅助标记（优先级之后，空格分隔）

| 标记 | 用途 |
|------|------|
| `风险 R-XX` | 引用风险登记簿编号 |
| `依赖 X-XX` | 引用前置任务编号 |
| `续 S{N} X-XX` | 跨 Sprint 续接 |
| `门槛 G-{N}` | 关联商用门禁（仅 V- 任务） |

### 6.3 示例（强制格式）

```
**P0** 100万行跨省过滤 P99≤500ms+零泄漏
**P0** 依赖 B-01/B-02，与 B-07 staging 模板对齐
**P1-Tech** §5.2.1
P1 续 S1 D-12a 核心实现
P1 风险 R-06
```

**禁止**：
- ❌ P0 任务无验收口径
- ❌ 备注写小说式描述（> 60 字）
- ❌ 备注留空（至少标 P1）
- ❌ 在备注中放链接（链接放任务描述）

## 7. Owner 列规范

- 单 Owner：`wangzk`
- 多 Owner：用 ` + ` 分隔（如 `qinhy + liulei + xw`），前后空格

**禁止**：
- ❌ "各组"、"AI Tester"、"PM"、"全员" 等非具体人员
- ❌ Owner 为空
- ❌ Owner 中夹杂角色名（如 `wangzk(部署)`、`wangzk - Developer`）
- ❌ 用姓名（如 `王志坤`），必须用 git_username

## 8. Deadline 列规范

- 同年：`M/D`（如 `6/15`、`6/30`）
- 跨年：`YYYY-MM-DD`（仅当 Sprint 跨年时）

**禁止**：
- ❌ "TBD"、"待定"、"未定"、空值
- ❌ 文字描述（"S2 中"、"6 月底"、"两周内"）
- ❌ 用工作日（"周五"）

## 9. 统计表数字自洽（违反即 P0）

每次更新看板必须重新核算 4 张统计表：

| 校验项 | 规则 |
|--------|------|
| Sprint 总数 | = 该 Sprint 所有任务表行数之和 |
| Sprint 状态分布 | `✅ + 🔵 + 🟡 + 🔴 + ⬜ = 总数` |
| 全战役合计 | = 各 Sprint 总数之和 |
| 按人员统计 | `各人员总数之和 = 全战役任务总数` |
| 按工作域统计 | `各工作域总数之和 = 全战役任务总数` |
| 完成率 | `✅ / 总数`，百分比取整（四舍五入） |

**多 Owner 任务计数**：同一任务有 N 个 Owner 时，每个 Owner 的"总数"+1（按人头计），但全战役任务总数不变。

## 10. AI 操作约束

### 10.1 必须做

1. 更新前 **Read 当前完整看板**，禁止仅凭记忆修改
2. 单次变更只动该动的行（精准变更），禁止重排无关任务
3. 变更后立即重算 4 张统计表，保持自洽
4. 同步更新元数据的"本次更新"和脚注的"最后更新"
5. LOCKED 标记的看板：变更前向 PM 确认（除非 PM 已授权）

### 10.2 禁止做

- ❌ 重命名 Sprint（如 "Sprint 1 · 功能迭代" → "S1 开发"）
- ❌ 重命名主线分组（如 "价值主线" → "D 主线"）
- ❌ 删除 LOCKED / FROZEN 状态标记
- ❌ 改变标题层级（H1/H2/H3）
- ❌ 调换结构块顺序
- ❌ 在不必要的情况下重新格式化整个看板
- ❌ 提交未通过统计自洽检查的变更

## 11. Reviewer 审查清单（看板变更必查）

Reviewer 审查看板变更时，以下任一违反即判 **P0 否决**：

- [ ] 8 个结构块完整且顺序正确
- [ ] **元数据 6 字段完整**（含「迭代开发版本号」，格式 `{产品}_{vX.Y.Z}_{YYYYMMDD}`）
- [ ] **任务表 7 列固定**（Sprint 0 允许 8 列加"主线"），含「对应研发系统需求号」列
- [ ] **「对应研发系统需求号」列**无空值（无对应填 `—`），格式为研发系统 ID
- [ ] 状态 emoji 仅来自 5 个枚举值
- [ ] 任务编号前缀来自 §5 注册表
- [ ] 备注列 P0 任务有验收口径
- [ ] Owner 列合规（git_username、` + ` 分隔）
- [ ] Deadline 列合规（M/D 格式，无 TBD）
- [ ] 4 张统计表数字自洽
- [ ] 脚注时间已更新
- [ ] LOCKED 标记未被擅自移除
- [ ] Sprint/主线名称未被重命名
- [ ] 标题层级未被改变

## 13. 新建看板流程

1. 复制 `kanban-template.md` 到 `reports/<YYYY>/knowledge/<战役>_kanban.md`
2. 替换所有占位符（`{...}`）
3. 按本规则填充任务行
4. 核算 4 张统计表自洽
5. 提交 PM 审批（architect 或 PM 角色）
6. PM 批准后标 LOCKED，进入正式维护周期
